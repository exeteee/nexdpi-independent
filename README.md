# NexDPI — независимый Android-проект

NexDPI — самостоятельное Android-приложение со своим интерфейсом и сетевым движком. Оно не скачивает, не встраивает, не модифицирует и не использует код ByeDPI или ByeDPIAndroid. Для работы не нужен VPS, собственный сервер или внешний VPN-шлюз.

## Текущая архитектура

После системного разрешения Android приложение создаёт виртуальный интерфейс `VpnService` и маршрутизирует через него IPv4 и IPv6. Сам NexDPI исключён из VPN, а выбранные в белом списке приложения работают напрямую.

- DNS: системные UDP-запросы разбираются локально и отправляются по DNS-over-HTTPS (RFC 8484) к стороннему провайдеру Cloudflare, Google или Quad9. Эти провайдеры получают DNS-запросы; NexDPI не хранит историю запросов. Используются резервирование провайдеров, фиксированные bootstrap IP для известных DoH-узлов, проверка TLS-сертификата, контроль DNS transaction ID и ответы SERVFAIL при отказе всех upstream. DNS-over-TCP на порту 53 пока отклоняется TCP RST.
- TCP: локальный userspace-мост устанавливает прямой защищённый сокет к адресу назначения, а приложение видит отдельное TCP-соединение внутри TUN. Реализованы ограничение потоков, sequence/ack, окно передачи, повторные отправки, закрытие FIN/RST и очистка при таймауте.
- TLS: первые байты TLS ClientHello временно буферизуются. Если SNI виден, движок исследует три варианта границы между двумя socket writes, отдельно для каждого имени узла, а затем использует ограниченную UCB-эвристику по факту получения ответа от удалённого узла. При ECH-расширении (даже если в наружном ClientHello видно публичное имя), отсутствии SNI или некорректном ClientHello данные передаются без разделения. Это лишь сигнал сетевого прохождения, не доказательство обхода DPI. Границы `write()` не гарантируют отдельные TCP-сегменты на физической сети.
- UDP: локальный relay использует защищённые прямые datagram-сокеты и восстанавливает исходный адресный кортеж для ответов. Это позволяет передавать обычный UDP и QUIC без собственного сервера, пока сеть разрешает прямое соединение с адресом назначения.
- Пакетная обработка: собственные IPv4/IPv6 парсеры, контрольные суммы, ограниченная повторная сборка входящих IP-фрагментов и фрагментация крупных ответных UDP-пакетов под MTU.
- Перегрузка: отдельные ограниченные DNS-, UDP- и TCP-пулы; UDP-датаграммы отправляются последовательно в порядке поступления, TCP-соединения обрабатываются параллельно, состояние потоков защищено блокировками. По умолчанию обслуживается не более 32 TCP и 24 UDP потоков одновременно; это ограничение уменьшает расход памяти на устройствах с небольшим объёмом ОЗУ.
- Whitelist: приложения из списка полностью исключаются из VPN-маршрутизации. Список хранится локально; изменения применяются при контролируемом переподключении.


## Поддержка прокси

В приложении есть отдельный менеджер прокси. Можно хранить несколько профилей, выбирать один активный, выключать его и удалять. Поддерживаются форматы Telegram deep link и обычные URI:

- **SOCKS5** — импорт `t.me/socks` / `tg://socks`, а также `socks5://` и `socks5h://`. Оба URI импортируются как SOCKS5; в текущем прозрачном VPN-пути доменное имя приложения уже разрешено до IP-адреса, поэтому отдельное поведение remote-DNS у `socks5h://` пока не реализовано. NexDPI использует SOCKS5 CONNECT для TCP и UDP ASSOCIATE для UDP. UDP работает только если сервер SOCKS5 действительно поддерживает UDP ASSOCIATE; если сервер отказал, UDP-поток завершается без прямого обхода прокси. SOCKS5 с логином/паролем поддерживается по RFC 1929.
- **MTProxy** — импорт `t.me/proxy` / `tg://proxy`, включая обычные, `dd` и `ee` secret. Профиль открывается штатной ссылкой в приложении Telegram, где Telegram выполняет MTProxy handshake. MTProxy не включается как системный туннель NexDPI и не перенаправляет браузер или другие приложения.
- **HTTP CONNECT** — ручной импорт URI вида `http://user:password@host:port`. NexDPI устанавливает HTTP CONNECT туннель для TCP. UDP через HTTP CONNECT не поддерживается и при выборе такого профиля блокируется, а не отправляется напрямую. Поддержана Basic-аутентификация. Учётные данные передаются прокси в HTTP-заголовке без TLS; используйте только доверенный сервер. HTTPS-прокси, Digest/NTLM и режим HTTP-only без CONNECT пока не реализованы.

Секреты и учётные данные профилей шифруются AES-GCM ключом Android Keystore. DNS-запросы самого NexDPI к DoH-провайдерам пока идут напрямую через underlying network и не используют выбранный proxy profile; это отдельное ограничение, а не полное проксирование DNS. Прокси-операторы могут видеть IP-адрес клиента, время подключения и целевые адреса/метаданные в пределах используемого протокола.

## Ограничения, которые нельзя скрывать

1. ICMP и другие IP-протоколы, кроме TCP и UDP, пока не пересылаются через VPN. Поэтому, например, ping и некоторые приложения, использующие дополнительные протоколы, могут не работать при включённом NexDPI. DNS-over-TCP на порту 53 также пока не реализован и отклоняется.
2. Приложения с собственным DoH/DoT не используют DNS-модуль NexDPI. Их TCP/UDP-соединения проходят через локальный relay, но DNS-запросы внутри таких соединений остаются зашифрованными. При этом системные DNS-запросы отправляются выбранному стороннему DoH-провайдеру — Cloudflare, Google или Quad9.
3. Если обнаружено ECH-расширение или SNI отсутствует, движок пропускает TLS-разделение и пересылает ClientHello без модификации; публичное имя во внешнем ECH ClientHello не принимается за реальное имя назначения. DNS-over-HTTPS не преодолевает блокировку IP-адреса назначения. Без внешнего сервера невозможно выдать пользователю другой внешний IP или перенести соединение в другую сеть.
4. Разделение TLS ClientHello — best-effort. Android/системный TCP-стек может объединить соседние socket writes в один TCP-сегмент; гарантировать фактическое разделение на линии нельзя.
5. Выбор TLS-варианта использует ответ удалённого узла как косвенный сигнал. Это не подтверждает успешность TLS-handshake или обход DPI: сетевой ответ может быть ошибкой самого сервера, а отсутствие ответа может быть вызвано другими причинами.
6. Полноценная Gradle-сборка Android и проверка на физическом устройстве ещё не выполнены в этой среде. Локальные 96 тестов и компиляция транспортных Kotlin-модулей не заменяют такую проверку.

NexDPI не обещает универсальный обход DPI. Реальная эффективность зависит от фильтрации конкретного оператора, протокола и адреса назначения.

## Сборка и проверка

Требуются JDK 17, Android SDK Platform 35 и Gradle 8.10.2:

```bash
gradle :app:testDebugUnitTest
gradle :app:assembleDebug
```

GitHub Actions workflow выполняет эти же Gradle-задачи и сохраняет debug APK как artifact. В локальной среде выполнены 96 тестов сетевой логики на Kotlin с тестовыми заглушками JUnit/OkHttp; транспортные модули отдельно скомпилированы, а VPN-service прошёл синтаксическую компиляцию на заглушках Android API. Это не Gradle-сборка и не проверка реального Android VPN-поведения.

Перед выпуском обязательны CI-сборка, проверка запуска/остановки/отзыва VPN-разрешения, переключение Wi-Fi/мобильной сети, работа IPv4/IPv6, проверка Private DNS и whitelist, а также измерения скорости, задержки, батареи и стабильности на реальном Android-устройстве.

## Принципы проекта

- Независимый исходный код и оригинальный интерфейс; никакой зависимости от ByeDPI.
- Никакого VPS и обязательного удалённого туннеля.
- Одна основная кнопка; пользовательские параметры — whitelist и необязательный менеджер прокси. Сохраняется до 32 профилей, активен один выбранный профиль.
- Внутреннее автоматическое переключение стратегий без ручного подбора параметров.
- Не объявлять стратегию успешной без измерений в реальной сети.
- При ошибке или отзыве разрешения закрывать TUN и транспортные потоки.
- Не отправлять список приложений, историю доменов и диагностику на внешний сервер.
